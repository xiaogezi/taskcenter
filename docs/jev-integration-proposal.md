# Jev 在 TaskCenter 中的渐进接入提案

状态：首期分类旁路已实现，默认未启动；其余三条试验线仍为待授权提案。核验日期：2026-09-20。

## 1. 结论与目标

建议接入，但把 Jev 定位为**可失效的语义建议层**：负责代码规则难以表达、结果能够校验的小判断。TaskCenter 继续负责身份、任务生命周期、模型配置、资源配额和验收。

本提案接受“尽快在真实工作中使用、出问题不影响整体流程”的目标。尽可能发挥 Jev 的作用，应以改善实际选择为衡量标准，而不是调用次数、覆盖模块数或标签数量。

推荐以四条试验线作为主方案：**模型路由建议、Agent 继续执行建议、风险筛查、输出检查**。四线可以共用调用、结果记录和故障隔离机制，但按数据授权和触发条件分别启用，不必一次全部上线。

共同原则是“多参与判断，少拥有决定权”：先观察，再由主 Agent 或用户采用，最后只放开经过验证的可逆应用。任务复用、上下文重排和 Skill 推荐保留为后续扩展，不再把首期价值限定在任务分类。

第一阶段只观察，不会自然产生主模型 token 节省。只有建议及时送达消费者、替代了原有工作或减少了无效尝试，才能主张效率收益。模型路由建议纳入首期，不等于首期自动切换执行模型。

- Jev 对中文、缩写、中英混合任务描述的判断质量。
- 新增建议是否改变了实际选择，而不是主 Agent 重复做相同判断。

- 标题/目标字段能否覆盖有用信息，或者需要更多输入；后者必须重新确认发送范围。
- 当前账户具体留存、地区和额度条件；已有余额与基础请求成功不能替代这些信息。

## 3. 四条主试验线

| 试验线 | 触发时机与最小输入 | Jev 的具体判断 | 结果消费者与允许动作 | 禁止越过的边界 |
|---|---|---|---|---|
| 模型路由建议 | 新任务创建/下一次派发前；title/goal，候选能力定义 | Choice：任务类别或所需能力档；信息不足可选 unknown/general | 主 Agent 对照现有选择；现有角色配置再映射可用模型 | 不修改集中配置、不绕过配额与退役模型限制、不热切换运行中的执行器 |
| Agent 继续执行建议 | 阶段检查点、重复失败后；目标及最近最多 3 步结构化摘要 | 分项 Noul：是否出现新证据、是否重复无变化尝试；必要时 Choice：继续/补证据/换方法/交还主 Agent/信息不足 | 主 Agent 决定下一步；提供建议后可继续原流程 | 不直接终止、重启、派发任务，不把“继续”视为新授权 |
| 风险筛查 | 拟执行动作确定后、执行前；动作目的、操作类型、目标环境、影响范围和可逆性摘要 | 分项 Noul：是否明确涉及删除、凭据、生产变更、迁移；缺信息另标 unknown | 主 Agent 核对已有权限和保护措施；必要时补充证据 | 不授予权限、不将低风险概率视为安全证明、不替代确定性安全门禁 |
| 输出检查 | 阶段报告或最终答复形成后；任务要求、输出主张、验证结果摘要及本地证据标识 | 分项 Noul：是否漏交付、主张与证据是否矛盾、是否把未验证写成已验证 | 实施 Agent 自检修正；人工确认有争议项 | 不替代测试、独立 Review 或最终 acceptance；不自动执行外部审查流程 |

标题和目标已经授权；后三线所需摘要与路由候选目录尚未授权外传。定义试验线和批准提案不等于自动开放新字段。无需为已授权的 title/goal 分类重复申请许可。

### 问题示例与解释边界

- 路由：“该目标主要需要实现、诊断还是设计能力？”而不是“哪家模型最好？”；候选能力与型号映射来自现有配置，不让模型编造型号。
- 继续执行：“最近三步是否得到可核验的新信息？”与“是否在条件未变化时重复同一失败动作？”分开判断。单次失败、必要重试和长耗时本身都不等于无效循环。
- 风险：“拟执行动作是否明确涉及生产数据删除？”按维度判断，不用一个综合分数抵消严重风险。目标环境未知时不能默认为开发环境。
- 输出：“声称完整测试通过，提供的验证摘要是否支持这一主张？”只检查收到的证据；不能把摘要一致性说成已确认源码正确或测试真实运行。

独立问题可在同一 state 下并行提问；依赖前一结果的问题由代码分阶段组合。没有合适证据时输出 unknown/不足，不以固定 confidence 阈值掩盖缺信息。

### 后续扩展

| 场景 | 判断与价值 | 扩展条件 |
|---|---|---|
| 描述充分性 | Noul：是否有明确交付物；辅助澄清 | 可复用已授权 title/goal；作为附加问题单独评估 |
| 任务复用 | 对现有候选判断是否同一交付目标 | 授权候选摘要，保留所有权与项目冲突规则 |
| 上下文重排 | Score：候选对当前问题的帮助程度 | 在 ProjectContext 边界内批准片段外传与预算规则 |
| Skill 推荐 | 任务与可用能力匹配 | 有漏用/误用证据，批准候选描述外传 |

## 4. 第一阶段的产品行为与采用方式

新任务仍按现有路径登记和派发。Jev 输出进入建议记录，只有用户或主 Agent 明确采用后，才影响下一项工作选择。

每条建议显示：试验线、绑定的任务/步骤/动作/输出版本、判断及分布、模型和 prompt 版本、生成时间、耗时与用量，并提供“采用 / 不采用 / 信息不足”和原因。Noul 没有独立 confidence，界面不能伪造统一 confidence 字段。

建议按三种模式渐进使用：

1. **观察**：后台记录，在评测报告中查看；不能声称已经省掉执行工作。
2. **辅助**：主 Agent 在自然检查点读取未过期建议；可修正下一步或答复。不等待未返回的建议，缺失时继续既有流程。
3. **可逆应用**：仅对单条试验线单独批准，例如预填类别或候选排序；权限、执行所有权和验收仍由原机制决定。

四线的时效要求不同：路由结果晚于派发只能用于复盘；继续执行结果晚于下一步骤不能影响该步骤；风险建议晚于动作执行不能算预防成功；输出建议晚于报告发出只能算事后发现。记录及时到达率，不能把迟到结果当作有效采用。

**旁路不等待与执行前保护存在取舍。** 首期接受建议来不及影响操作，因此风险筛查是补充观察，不是必经安全检查。将来若要求动作必须等待 Jev，即改变主流程依赖，需要另做方案选择，不能偷偷加入同步门禁。

第一批用报告收集反馈，持续使用再接现有详情页或 Agent 的 prepare/checkpoint 返回。不为读取建议再制造一轮完整 Agent 调用；只有日志、没有消费者不算业务闭环。

输入变化即标记建议过期：分别绑定目标摘要、步骤窗口、拟执行动作、输出与证据版本的哈希。相同任务 ID 不足以证明建议仍适用。迟到结果不得改写已启动模型、已执行动作或任务状态。

## 5. 架构选择

| 方案 | 数据流 | 优点 | 代价与边界 | 结论 |
|---|---|---|---|---|
| A. 独立事件观察器 | 本地新任务/经授权的结构化检查点 → 旁路进程 → 官方 API → 本地建议记录 | 不改主服务请求链；启动和停止独立；网络异常不传播到任务创建 | 需要维护进程与日志；停机/轮转可能漏样本；展示接口后续接入 | 推荐首期 |
| B. 控制服务异步钩子 | 落账后排队调用 API | 更直接绑定业务事件和任务详情 | 即使不 await，也共享堆、队列、文件系统和进程异常风险；需受控部署 | 观察收益明确后再考虑 |
| C. 手工批量脚本 | 选定样本 → API → 报告 | 最低运行维护成本，利于重复评测 | 不持续参与新任务，难观察真实采用情况 | 用作评测工具，不作为最终接入 |

现有 task.create 只能支撑分类；后三线需要生产方在检查点提供字段白名单摘要，不能由观察器抓取完整 Session 来补齐。摘要投递也必须不阻塞主流程。先记录建议，后把读取入口接入现有检查点；四线共用简单调用和记录函数，不预建通用决策平台。

推荐保留 Node.js 原生 fetch、文件 API 和现有 JSONL 习惯。无需新增数据库、消息队列、通用插件框架或 SDK；API 固定且调用简单。官方 SDK 的默认重试会改变请求次数和时间预算，首期直接 HTTP 更易控制。

```mermaid
flowchart LR
  A[任务创建] --> B[本地账本落账]
  B --> C[原有派发与执行]
  B -.只读观察新增事件.-> D[独立 Jev 观察器]
  C -.另行授权的步骤、动作和输出摘要.-> D
  D --> E[按试验线选择已授权字段]
  E --> F[TypeSafe 官方 API]
  F --> G[本地建议与用量记录]
  G --> H[报告或建议卡]
  H -.人工采用后才有收益.-> C
```

旁路结果不能写回原任务状态，不能修改 `config/model-roles.json`，不能提交 acceptance 或伪装为 review 证据。

| 新任务分类 | 已授权 | title、goal | 原始事件整体、Session 正文 |

| 风险筛查 | 待授权 | 操作类别、环境、影响对象类型、可逆性、未知字段 | 密钥、真实敏感路径、原始 shell 命令或 SQL |
| 输出检查 | 待授权 | 交付要求、输出主张、验证状态摘要、脱敏证据引用 | 完整源码、diff、原始报告全文与原始日志 |

新增摘要由生产方显式构造并标明“观察事实 / Agent 自述 / 未验证”，字段缺失保持未知。原始证据留本地，Jev 不能自行证明摘要来源真实。每条线独立启用；缺授权则跳过该线，不阻止已经授权的分类。

初期固定规则：

- 精确匹配已授权 workspace，不自动扩展到其他项目或 worktree。
- 不补传历史任务，不读 Session 正文、源码或认证配置。
- 当前分类发送对象显式构造为 `{title, goal}`，不扩展整个事件对象。两字段分别限制在 200、1000 字符以内，与当前账本边界一致。
- API Key 由进程环境 `TYPESAFE_API_KEY` 提供；不写入代码、命令参数、审计日志或网页。
- 只连接 `https://api.typesafe.ai/v1/systemone`，拒绝重定向；不提供任意 endpoint 配置。
- 日志记录 task/event 标识、输入摘要哈希、prompt 版本、模型版本、结果、用量、耗时和安全错误码。标题与目标无需复制进日志；需要复核时在本地按任务标识查原记录。
- 标题和目标本身仍可能携带业务信息或秘密。“只发两字段”不是自动脱敏证明。疑似凭据应跳过并记原因；检测无法保证覆盖所有敏感内容。
- 本地文件 0600、目录 0700；日志限制容量，运行账户权限不提升。

官方声明不使用客户输入训练，但不能据此假设普通账户是零留存。公开隐私政策说明数据留存与美国处理；企业 ZDR 需以账户合同为准。本提案不主张本地化处理或零留存。[官方隐私政策](https://typesafe.ai/legal/privacy-policy)

上下文片段、历史任务候选、错误日志和 diff 都不在当前外传授权内。扩展用途先明确最小字段和数据所有者，再实施。

## 7. 故障隔离与退出机制

“不影响整体流程”定义为：Jev 不参与核心成功条件、失败不修改任务状态、关闭后原流程无需修复即可继续。独立进程仍共享机器资源，不能承诺 CPU、内存和磁盘影响绝对为零。

| 故障或风险 | 预期处理 | 可验证证据 |
|---|---|---|
| 超时/断网/DNS/TLS 异常 | 单次最多 5 秒，取消请求；无自动重试 | 故障注入后观察器可继续处理新任务 |
| 401/403 | 提醒凭据不可用，停止进一步请求，等待人工修复 | 失败后没有持续付费/刷日志循环 |
| 429/连续 5xx | 暂停一段时间，保持原流程；不立即连续重试 | 跳过原因与下次可用时间可见 |
| 响应畸形、非预期类别、超大响应 | 丢弃建议，只记错误码 | schema/分布/大小限制测试 |
| 请求尚未完成又有任务到达 | 首期并发 1，无等待队列，记 busy 跳过 | 内存不随任务洪峰增长 |
| 重复事件 | 按任务和输入版本避免重复请求 | 幂等测试；若扩大运行规模，去重需有持久化策略 |
| 配额或次数上限 | 首期四线合计每轮最多 100 请求；达到上限停止调用并报告 | 不把上限后的缺样误判为服务成功 |
| 文件写入失败/磁盘不足 | 旁路停止并输出固定错误码，不写核心账本 | 写失败测试 |
| 进程退出/机器休眠 | 主服务继续；漏样在报告中说明 | 进程状态、心跳与采样覆盖指标 |
| 日志轮转/事件截断 | 首期允许跳过，不追历史，报告缺口 | 轮转测试与覆盖率记录 |
| 建议与输入版本不一致 | 标记过期，不应用 | 输入哈希核对 |

首期以进程启停作为总开关；各试验线增加独立启用状态，某条效果不好可以单独关闭。后续若接入服务内钩子，再引入该消费者的功能开关；不为旁路预先改造全局配置系统。

次数上限目前是每轮而不是每日预算，重启会重置，不能称为严格费用硬门禁。持续运行阶段应增加持久预算计数或使用提供商账户支出上限，并核实账户是否提供该能力。

回滚顺序：停止旁路 → 验证 TaskCenter 仍健康 → 保留本地报告供分析。无需回滚任务账本；已传出的数据无法通过关闭开关撤回。旧建议不得在重启后自动成为执行命令。

## 8. 如何验证价值

### 第一轮：15 条真实新任务

以 15 个真实任务作为第一轮样本池，按已授权字段分别评估四线。每个任务不要求强行触发四条线；没有事件或授权的线标为未评估，不记为成功。自然收集当前项目新任务，覆盖局部修复、文档、测试、架构、迁移、未知根因和描述含糊情况。自然样本没有覆盖的类别，用单独标记的合成样本补充；二者不混成一个准确率。

在看 Jev 结果前，人工为各线标注预期判断或允许结果集合；不能先看模型结果再补标签。路由类别由人校验，循环判断核对新证据，风险核对实际动作，输出核对本地验证记录。主 Agent 自述和现有类别只是对照，不是真值。

每条记录：

```text
task_id / experiment_line / checkpoint_id / input_hash / prompt_version / model_version
expected_labels / ambiguity / jev_choice / probabilities / confidence
agent_actual_decision / human_feedback / adopted / adoption_effect / arrived_before_action
status / skip_reason / latency_ms / input_tokens / output_tokens
```

指标分三层：

| 层次 | 指标 | 防止的误读 |
|---|---|---|
| 可运行 | 符合条件任务数、请求数、成功率、busy/停机漏样、耗时和成本 | 只看成功请求掩盖采样缺口 |
| 判断质量 | 人工可接受比例、各类别错误、信息不足识别、过度自信错误 | confidence 不是正确率；总体准确率掩盖稀有风险类别 |
| 业务价值 | 被采用的建议、纠正的选择、减少的重复任务或查找时间、新增纠错成本 | 标签生成量不是效益；采纳率也不等于正确率 |

### 分线成功标准

| 试验线 | 要测的直接指标 | 主要失败形式 | 首轮应回答的问题 |
|---|---|---|---|
| 模型路由 | 类别/能力建议可接受率；采用后的合格交付总成本、返工量 | 低估任务、推荐不可用能力、没有替代任何工作 | 是否纠正了至少一项有意义的选择？ |
| 继续执行 | 无效循环发现率、误报率、及时到达率、采用后省掉的无效步骤 | 把必要探索当循环，或建议继续但没有新证据 | 是否减少无效尝试且没有打断必要探索？ |
| 风险筛查 | 已标注风险召回率、误报率、未知环境识别率 | 漏掉重大风险或产生虚假的安全感 | 是否补到了现有检查之外的有效提醒？ |
| 输出检查 | 有效矛盾/遗漏检出率、误报率、实际修正数 | 把摘要缺失当事实错误，或假通过掩盖缺证据 | 是否纠正了缺证据的声明且没有增加无益返工？ |

分别统计任务数和判断次数：15 个任务可能产生不同数量的检查点，不能合并为一个“准确率”。循环/风险/输出的负例与误报同样需要标注。不同线不共用分类的 85% 目标，也不设置一个通用 confidence 放行阈值。

15 条是可用性与错误形态检查，不是生产质量证明。即便 15 次无错，在独立同分布等假设下，常用“3/n”近似给出的错误率上界仍约 20%；自然任务还可能存在偏样。

首轮结束必须明确：继续、修改问题再试，或者停止当前场景。对每条已测试线分别列出建议是否影响了具体工作；若没有，不能以“API 很便宜”认定值得持续维护。

### 第二轮：低风险可见建议

只在第一轮确认结果可理解、无明显系统性偏差后，收集约 50–100 条自然任务，并让用户实际选择是否采用。样本数只是复盘触发点，不是自动放量门槛。

不要一边不断改 prompt，一边汇总成同一版本的准确率。保留固定验证集，分别报告 prompt/model 版本；中文、中英混合、描述稀疏分开看。

建议预先锁定的试点目标（待实测调整，非已达到）：

- 核心任务失败归因于 Jev 的数量为 0；凭据泄漏或未授权数据发送一例即停。
- 观测成功率达到 95% 以上时再评价模型质量；不足时先排除网络/配置问题。
- 分类人工可接受比例目标 85% 以上，并逐条解释复杂任务误判；不能只凭总体达标放开自动路由。
- 有效建议采用后节省的人工时间，大于阅读建议、纠错和维护花费。

### 第三轮：只放开可逆应用

可候选：建议卡默认预填类别、复用候选排序、上下文候选内部重排。仍保留原候选和撤销入口，不自动切换任务所有权或降低验证强度。

模型路由建议首期已经观察；升级为自动应用前要另做端到端比较：以交付质量和返工后的总成本为指标，不能用路由分类准确率替代。主 Agent 仍完整读任务时，Jev 的分类不会自动节省那次理解成本。

## 9. 成本与收益估算

2026-09-20 官方模型页标价：输入每百万 tokens 0.042 美元，输出不收费。固定 `jev-1.13.0` 便于对照，升级版本单独比较。[官方模型说明](https://docs.typesafe.ai/models)

下面是计算示例，不是测量结果，未含税费、汇率、账户差异或其他服务：

| 请求量 | 假设每次输入 | 理论 API 成本 |
|---|---|---|
| 15 次 | 1000 tokens | 0.00063 美元 |
| 100 次 | 1000 tokens | 0.0042 美元 |
| 1000 次 | 1000 tokens | 0.042 美元 |

一个任务可能在四个时点触发多次请求，不能把上表的请求量当作任务数。总预算按四线合计控制，并单列每条线的用量。

实际计费输入包含问题与 rubric，不能只按标题长度估算；多问题也不是免费。优先使用响应 usage 汇总，费用标为估算，不把余额、credits、美元混成同一单位。

更重要的成本是工程维护、网络依赖、观察与误判。收益应按下式核算：

```text
净收益 = 确实省掉的人工/模型工作
       - Jev 请求成本
       - 阅读建议与纠错成本
       - 维护及故障处理成本
```

### 任务复用作为后续扩展的价值

现有 `semanticScore` 基于词项重合。它对字面接近有效，但“恢复暂停任务”和“接着把上次没做完的继续”可能词面不同。Jev 可以在本地规则已经认可的候选里判断是否同一交付目标。

保留项目、workspace、owner、Session 和 delegation 冲突规则。Jev 只能重排或补充建议，不能因为语义相似就允许跨所有者接手。

这一阶段需要单独的候选快照与授权：现有 Top-K 可能漏掉真实候选，Jev 无法找回从未收到的候选；重排成功不能证明召回充分。也不能把语义相近等同于同一交付生命周期。

## 11. 首期实现与落地差距

首期旁路已实现但默认未启用：

- `scripts/jev-advisor.mjs`：仅分类；独立 tail；精确 workspace 限制；单并发；5 秒超时；每轮 100 次上限；401/403 自行停用、429/529 冷却；响应校验；疑似凭据跳过；本地日志与报告。
- `npm run jev:watch` 与 `npm run jev:report`：手动启动和查看本地试点结果。启动时必须显式提供 `TASKCENTER_JEV_ENABLED=true`、`TASKCENTER_JEV_WORKSPACE` 与进程环境中的 `TYPESAFE_API_KEY`；不会写入仓库或主服务配置。
- `tests/jev-advisor.test.mjs`：11 项定向测试覆盖字段白名单、API 失败、超时、凭据跳过、认证停用、限流冷却、去重、尾部增量读取、日志轮转与权限等。
- 未改变主服务或原任务流程，未启动试点；真实最小请求由已经授权的运行命令在用户环境中触发。

这些只证明草稿的局部行为，不能宣布接入完成。继续实施前仍需处理：

1. 首期只覆盖任务分类，不覆盖完整模型路由建议、继续执行、风险筛查和输出检查；后三线的摘要采集、外传授权、触发器与消费者均未实现。
2. 输入版本标识、过期提示、及时到达率和人工反馈尚未实现。
3. 跨重启预算约束和连续 5xx 冷却尚未实现；当前的认证停用与限流冷却只在单次运行内生效。
4. 当前精确 workspace 匹配不包含 worktree；是否扩展必须显式决定。
5. 重启不补历史，轮转允许漏样；需要覆盖率与停机可见性，不能只统计收到的成功结果。
6. 当前去重内存有界，日志最多保留两段；适合有限试点，不是永久证据系统。
7. PID 残留、重复启动、关闭期间在途请求、主服务健康不受影响等需端到端验收。
8. 标题/目标内潜在秘密采用保守跳过规则，启动认证环境及本机真实调用仍需验证。
9. 缺少建议消费者时只能算观察工具，不算工作流效能改进。

首期实现不代表四线均已接入，也不改变原有路由、执行、安全或验收权限。

### 建议决策

推荐以四条主试验线推进 A+B：复用一套有界调用、隔离和观察机制，先运行已授权的标题/目标分类；补齐并确认三类新增摘要及路由候选定义后，逐线启用。以 15 个任务复盘每条线的及时性、误判和实际采用价值，允许分别保留、调整或关闭，不要求四线一起成功。

当前已授权：新任务 title/goal 外传、分类旁路、失败不影响主流程；首期实现已就绪，默认未启动。尚待实施前确认的是新增数据字段和应用权限，而不是是否允许研究这些场景。纯旁路观察不自动升级成模型切换、执行中止、安全许可或最终验收。

任务复用和上下文重排仍是后续候选；不让这些扩展分散四条主线的第一轮评测，也不把任何尚未完成的草稿算作已接入。
