# Jev 在 TaskCenter 中的渐进接入提案

状态：待评审提案，不表示已启用。核验日期：2026-09-20。

## 1. 结论与目标

建议接入，但把 Jev 定位为**可失效的语义建议层**：负责代码规则难以表达、结果能够校验的小判断。TaskCenter 继续负责身份、任务生命周期、模型配置、资源配额和验收。

本提案接受“尽快在真实工作中使用、出问题不影响整体流程”的目标。尽可能发挥 Jev 的作用，应以改善实际选择为衡量标准，而不是调用次数、覆盖模块数或标签数量。

推荐顺序：

1. **任务理解旁路**：分类和描述充分性建议，先建立可观察的真实调用。
2. **任务复用建议**：在已有候选中识别同一交付目标，减少重复开任务和人工查找。
3. **上下文候选重排**：在 ProjectContext 所属边界内单独试点，改善有限上下文预算的使用。
4. 前三项确有收益后，再讨论有限的自动应用。不要先让 Jev 控制模型派发、安全授权或验收。

第一阶段只观察，不会自然产生主模型 token 节省。只有后续消费者确实使用建议，替代了原有工作，才能主张效率收益。

### Agent 推断

- 标题与目标足以做粗分类，通常不足以判断真实修改风险、工作量或代码正确性。
- 与新增一个分类标签相比，“从近似描述中识别已有任务”更可能产生可感知收益，因为已有明确业务入口和词项匹配基线。
- 上下文重排潜在收益较高，但涉及另一个组件的检索、预算和知识权威层，不能在 TaskCenter 中另建一套并行上下文系统。
- 独立旁路进程比在任务请求中同步等待 Jev 更符合当前故障隔离目标。

### 待验证假设

- Jev 对中文、缩写、中英混合任务描述的判断质量。
- 新增建议是否改变了实际选择，而不是主 Agent 重复做相同判断。
- 实际请求延迟、有效回答率、人工纠错负担与成本。
- 标题/目标字段能否覆盖有用信息，或者需要更多输入；后者必须重新确认发送范围。
- 当前账户具体留存、地区和额度条件；已有余额与基础请求成功不能替代这些信息。

## 3. 场景全景与优先级

| 场景 | Jev 判断 | 消费者与收益 | 输入边界 | 建议 |
|---|---|---|---|---|
| 任务分类 | Choice：主要工作类别 | 对照主 Agent 类别，发现误分和缺省类别 | 新任务 title/goal | P0：低成本建立观察闭环 |
| 描述充分性 | Noul：是否有明确交付目标 | 非阻塞提示缺信息，减少反复澄清 | 同一 title/goal | P0 提案：与分类同请求；尚未实现 |
| 任务复用 | Noul：与候选是否同一交付目标 | 对已有 Top-K 候选补充语义建议 | 新任务与候选摘要 | P1：直接业务价值更明确；候选数据外传需新增授权 |
| 上下文重排 | Score：候选对当前问题的帮助程度 | ProjectContext 调整候选顺序，节省阅读或上下文预算 | 查询与候选片段 | P2：在 ProjectContext 单独试点 |
| Skill 推荐 | Choice/多项 Noul：匹配哪类能力 | 提醒主 Agent 可用能力 | 任务摘要及 Skill 描述 | P2：只有确有漏用/误用证据时再做 |
| 风险提示 | 分项 Noul：描述是否明确涉及迁移、安全等 | 提示补充证据，不签发“安全”结论 | 摘要；不足时明确未知 | 可跟随 P1 验证，禁止当门禁 |
| 模型自动路由 | 分类结果参与实际选择 | 可能降低执行成本，也可能增加返工 | 还需要任务结果与模型质量基线 | 暂不纳入首期 |
| Review、授权、验收 | 是否允许执行、是否真正完成 | 错误会影响治理真实性 | 需要独立证据和权限 | 不由 Jev 决定 |

P0/P1/P2 是提案优先级，不代表这些功能已授权全部实施。当前明确授权的数据仅为新任务标题与目标。

## 4. 第一阶段的产品行为

新任务仍按现有路径登记和派发。旁路观察到该任务后，给出建议。结果晚到、失败、不可用时，任务照常继续。

首期建议展示：

- Jev 建议类别、概率分布、confidence、模型版本和生成时间。
- 描述充分性信号（新增提案项）；低概率只表示“建议补充描述”，不强制阻断任务。
- 主 Agent 实际类别；未知就显示未记录，不把缺省 `general` 当成人工判断。
- “采用 / 不采用 / 信息不足”反馈，以及简短原因。
- 请求状态、耗时、token 用量、输入版本是否仍匹配。

第一批 15 个样本用报告收集反馈，不必先做新看板。准备持续使用时，再把紧凑建议卡接到现有任务详情；仅有 JSONL 日志、无人查看，不算形成业务闭环。

**迟到结果不得更改已启动的模型或任务状态。** 任务标题/目标更新后，旧建议标记过期；首期可以不自动重算，但不能继续显示为当前建议。

问题设计避免把多件事混为一谈：

```text
Choice：这个标题与目标描述的主要交付类别是什么？
Noul：仅根据标题与目标，是否能明确识别预期交付物？
```

“缺少完整验收条件”不等于“任务描述完全无法理解”；“架构任务”也不等于“必须用某个昂贵模型”。

## 5. 架构选择

| 方案 | 数据流 | 优点 | 代价与边界 | 结论 |
|---|---|---|---|---|
| A. 独立事件观察器 | 本地 task.create → 旁路进程 → 官方 API → 本地建议记录 | 不改主服务请求链；启动和停止独立；网络异常不传播到任务创建 | 需要维护进程与日志；停机/轮转可能漏样本；展示接口后续接入 | 推荐首期 |
| B. 控制服务异步钩子 | 落账后排队调用 API | 更直接绑定业务事件和任务详情 | 即使不 await，也共享堆、队列、文件系统和进程异常风险；需受控部署 | 观察收益明确后再考虑 |
| C. 手工批量脚本 | 选定样本 → API → 报告 | 最低运行维护成本，利于重复评测 | 不持续参与新任务，难观察真实采用情况 | 用作评测工具，不作为最终接入 |

推荐保留 Node.js 原生 fetch、文件 API 和现有 JSONL 习惯。无需新增数据库、消息队列、通用插件框架或 SDK；API 固定且调用简单。官方 SDK 的默认重试会改变请求次数和时间预算，首期直接 HTTP 更易控制。

```mermaid
flowchart LR
  A[任务创建] --> B[本地账本落账]
  B --> C[原有派发与执行]
  B -.只读观察新增事件.-> D[独立 Jev 观察器]
  D --> E[标题与目标白名单]
  E --> F[TypeSafe 官方 API]
  F --> G[本地建议与用量记录]
  G --> H[报告或建议卡]
  H -.人工采用后才有收益.-> C
```

旁路结果不能写回原任务状态，不能修改 `config/model-roles.json`，不能提交 acceptance 或伪装为 review 证据。

## 6. 数据、认证和运行边界

已获用户授权：发送当前项目新任务的 title、goal 到 TypeSafe 官方 API。

初期固定规则：

- 精确匹配已授权 workspace，不自动扩展到其他项目或 worktree。
- 不补传历史任务，不读 Session 正文、源码或认证配置。
- 发送对象显式构造为 `{title, goal}`，不扩展整个事件对象。两字段分别限制在 200、1000 字符以内，与当前账本边界一致。
- API Key 由进程环境 `TYPESAFE_API_KEY` 提供；不写入代码、命令参数、审计日志或网页。
- 只连接 `https://api.typesafe.ai/v1/systemone`，拒绝重定向；不提供任意 endpoint 配置。
- 日志记录 task/event 标识、输入摘要哈希、prompt 版本、模型版本、结果、用量、耗时和安全错误码。标题与目标无需复制进日志；需要复核时在本地按任务标识查原记录。
- 标题和目标本身仍可能携带业务信息或秘密。“只发两字段”不是自动脱敏证明。疑似凭据应跳过并记原因；检测无法保证覆盖所有敏感内容。
- 本地文件 0600、目录 0700；日志限制容量，运行账户权限不提升。

官方声明不使用客户输入训练，但不能据此假设普通账户是零留存。公开隐私政策说明数据留存与美国处理；企业 ZDR 需以账户合同为准。本提案不主张本地化处理或零留存。[官方隐私政策](https://typesafe.ai/legal/privacy-policy)

上下文片段、历史任务候选、错误日志和 diff 都不在当前外传授权内。扩展用途先明确最小字段和数据所有者，再实施。

## 7. 故障隔离与退出机制

“不影响整体流程”定义为：Jev 不参与核心成功条件、失败不修改任务状态、关闭后原流程无需修复即可继续。独立进程仍共享机器资源，不能承诺 CPU、内存和磁盘影响绝对为零。

| 故障或风险 | 预期处理 | 可验证证据 |
|---|---|---|
| 超时/断网/DNS/TLS 异常 | 单次最多 5 秒，取消请求；无自动重试 | 故障注入后观察器可继续处理新任务 |
| 401/403 | 提醒凭据不可用，停止进一步请求，等待人工修复 | 失败后没有持续付费/刷日志循环 |
| 429/连续 5xx | 暂停一段时间，保持原流程；不立即连续重试 | 跳过原因与下次可用时间可见 |
| 响应畸形、非预期类别、超大响应 | 丢弃建议，只记错误码 | schema/分布/大小限制测试 |
| 请求尚未完成又有任务到达 | 首期并发 1，无等待队列，记 busy 跳过 | 内存不随任务洪峰增长 |
| 重复事件 | 按任务和输入版本避免重复请求 | 幂等测试；若扩大运行规模，去重需有持久化策略 |
| 配额或次数上限 | 首期每轮最多 100 请求；达到上限停止调用并报告 | 不把上限后的缺样误判为服务成功 |
| 文件写入失败/磁盘不足 | 旁路停止并输出固定错误码，不写核心账本 | 写失败测试 |
| 进程退出/机器休眠 | 主服务继续；漏样在报告中说明 | 进程状态、心跳与采样覆盖指标 |
| 日志轮转/事件截断 | 首期允许跳过，不追历史，报告缺口 | 轮转测试与覆盖率记录 |
| 建议与输入版本不一致 | 标记过期，不应用 | 输入哈希核对 |

首期以进程启停作为总开关。后续若接入服务内钩子，再引入该消费者的功能开关；不为旁路预先改造全局配置系统。

次数上限目前是每轮而不是每日预算，重启会重置，不能称为严格费用硬门禁。持续运行阶段应增加持久预算计数或使用提供商账户支出上限，并核实账户是否提供该能力。

回滚顺序：停止旁路 → 验证 TaskCenter 仍健康 → 保留本地报告供分析。无需回滚任务账本；已传出的数据无法通过关闭开关撤回。旧建议不得在重启后自动成为执行命令。

## 8. 如何验证价值

### 第一轮：15 条真实新任务

自然收集当前项目新任务，覆盖局部修复、文档、测试、架构、迁移、未知根因和描述含糊情况。自然样本没有覆盖的类别，用单独标记的合成样本补充；二者不混成一个准确率。

在看 Jev 结果前，由人标注预期类别或允许类别集合，并标记信息不足。主 Agent 的现有分类只是对照，不是真值。

每条记录：

```text
task_id / input_hash / prompt_version / model_version
expected_labels / ambiguity / jev_choice / probabilities / confidence
agent_actual_class / human_feedback / adopted / adoption_effect
status / skip_reason / latency_ms / input_tokens / output_tokens
```

指标分三层：

| 层次 | 指标 | 防止的误读 |
|---|---|---|
| 可运行 | 符合条件任务数、请求数、成功率、busy/停机漏样、耗时和成本 | 只看成功请求掩盖采样缺口 |
| 判断质量 | 人工可接受比例、各类别错误、信息不足识别、过度自信错误 | confidence 不是正确率；总体准确率掩盖稀有风险类别 |
| 业务价值 | 被采用的建议、纠正的选择、减少的重复任务或查找时间、新增纠错成本 | 标签生成量不是效益；采纳率也不等于正确率 |

15 条是可用性与错误形态检查，不是生产质量证明。即便 15 次无错，在独立同分布等假设下，常用“3/n”近似给出的错误率上界仍约 20%；自然任务还可能存在偏样。

首轮结束必须明确：继续、修改问题再试，或者停止当前场景。至少列出一个具体建议影响了哪项工作；若没有，不能以“API 很便宜”认定值得持续维护。

### 第二轮：低风险可见建议

只在第一轮确认结果可理解、无明显系统性偏差后，收集约 50–100 条自然任务，并让用户实际选择是否采用。样本数只是复盘触发点，不是自动放量门槛。

不要一边不断改 prompt，一边汇总成同一版本的准确率。保留固定验证集，分别报告 prompt/model 版本；中文、中英混合、描述稀疏分开看。

建议预先锁定的试点目标（待实测调整，非已达到）：

- 核心任务失败归因于 Jev 的数量为 0；凭据泄漏或未授权数据发送一例即停。
- 观测成功率达到 95% 以上时再评价模型质量；不足时先排除网络/配置问题。
- 分类人工可接受比例目标 85% 以上，并逐条解释复杂任务误判；不能只凭总体达标放开自动路由。
- 有效建议采用后节省的人工时间，大于阅读建议、纠错和维护花费。

### 第三轮：只放开可逆应用

可候选：建议卡默认预填类别、复用候选排序、上下文候选内部重排。仍保留原候选和撤销入口，不自动切换任务所有权或降低验证强度。

模型路由要另做端到端比较：以交付质量和返工后的总成本为指标，不能用路由分类准确率替代。主 Agent 仍完整读任务时，Jev 的分类不会自动节省那次理解成本。

## 9. 成本与收益估算

2026-09-20 官方模型页标价：输入每百万 tokens 0.042 美元，输出不收费。固定 `jev-1.13.0` 便于对照，升级版本单独比较。[官方模型说明](https://docs.typesafe.ai/models)

下面是计算示例，不是测量结果，未含税费、汇率、账户差异或其他服务：

| 请求量 | 假设每次输入 | 理论 API 成本 |
|---|---|---|
| 15 次 | 1000 tokens | 0.00063 美元 |
| 100 次 | 1000 tokens | 0.0042 美元 |
| 1000 次 | 1000 tokens | 0.042 美元 |

实际计费输入包含问题与 rubric，不能只按标题长度估算；多问题也不是免费。优先使用响应 usage 汇总，费用标为估算，不把余额、credits、美元混成同一单位。

更重要的成本是工程维护、网络依赖、观察与误判。收益应按下式核算：

```text
净收益 = 确实省掉的人工/模型工作
       - Jev 请求成本
       - 阅读建议与纠错成本
       - 维护及故障处理成本
```

### 为什么任务复用值得优先研究

现有 `semanticScore` 基于词项重合。它对字面接近有效，但“恢复暂停任务”和“接着把上次没做完的继续”可能词面不同。Jev 可以在本地规则已经认可的候选里判断是否同一交付目标。

保留项目、workspace、owner、Session 和 delegation 冲突规则。Jev 只能重排或补充建议，不能因为语义相似就允许跨所有者接手。

这一阶段需要单独的候选快照与授权：现有 Top-K 可能漏掉真实候选，Jev 无法找回从未收到的候选；重排成功不能证明召回充分。也不能把语义相近等同于同一交付生命周期。
