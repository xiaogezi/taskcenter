# TaskCenter 开源机制借鉴与链路优化提案

状态：A/Q1 已选择并实施；其余切片仍为提案。日期：2026-09-20。

初始交付仅建立提案；后续 Q1 实施记录见第 10 节，不代表其余方案已实施或正式服务已部署。本文不替代 AGENTS.md、既有权限合同和 CONTRIBUTING.md 的发布规则。

## 1. 决策摘要

推荐保留当前 TaskCenter、Node.js、React/TypeScript、JSON/JSONL 账本和同进程静态 Harness；借鉴开源机制改进已有路径，不引入第二套任务中心、数据库、调度服务或通用插件系统。

建议顺序：

1. 查询与展示：精准读取、可选摘要、保留加载错误、正确表达模型来源、展开已有活动事实。
2. 回执恢复：核对现有人工补报链路，补齐稳定事件标识与只重报结果的确定性入口。
3. 条件优化：仅针对复现问题改进 Hook 解释、同环境预检、文档预检；证据复用另行决策。

已覆盖的轮询刷新、Harness 能力声明、重复领取与服务端事件去重不重新立项。Review 由用户安排，不自动启动，不成为普通完成、提交或授权部署的阻塞条件；独立验收继续遵守现行授权规则。

## 4. 目标、非目标与成功口径

### 目标

- 用户能区分路由选择、启动事实、运行回执、验证、Review 和验收。
- 模型查询一个任务时不在内部拉取全部任务，简单问题只返回必要事实。
- 结果回写失败后可以核实并补报，避免将通信失败错误升级为再次执行。
- 只读探测、预检与文档输入问题可以在准确边界内解释和定位。

### 非目标

不换语言、数据库、模型角色、权限制度或部署拓扑；不自动安排 Reviewer；不迁移历史任务；不增加后台自动重试服务；不读取认证文件；不对模型物理身份作客户端报告之外的保证；不承诺通用 exactly-once；不把验证缓存加入本批实现。

### 测量方法

先记录基线，再用相同脱敏夹具、相同字段需求和运行环境对比。内部 HTTP 字节数、模型收到的 UTF-8 字节数、工具调用次数、处理耗时分别记录；字节数不能直接冒充 token。只有固定 tokenizer 时才报告 token。不得事先宣称节省比例。

- 查询场景：下一步是什么、为什么阻塞、缺什么验证、谁实际执行、最近发生什么。
- 规模：少量任务与至少千条合成任务；目标任务相同，逐步增加无关历史。
- 目标：单任务内部响应不随无关任务数量增长；摘要不包含全部历史；简单场景在 1—2 次工具调用获得足够事实。这是待验收目标，不是现有收益。
- 文件账本仍可能整文件读取，因此响应缩小不能证明磁盘读取或端到端耗时为 O(1)。只有测量证明瓶颈后才另议索引。

## 5. 第一阶段：查询与真实状态展示

### Q1 精准查询与兼容摘要

责任位置：`taskcenter-mcp.mjs`、`control-server.mjs` 和已有投影。先复用单任务 GET，不新建查询服务。

推荐契约：现有参数和返回外层结构保持兼容；增加显式 `view=summary|full`，旧调用省略时保留 full。新调用指引优先 summary。不要静默把现有调用默认改成摘要。后续改默认需单独评估消费者。

- 提供 task_id 时走单任务读取；同时提供 session_id 时仍校验交集，不返回其他 Session 的任务。
- 单任务与原全量路径的投影、归档可见性和字段补全并非天然等价：前者使用 `loadTasks` 与 `taskPresentation`，后者无参数时使用 `loadVisibleTasks`。切换前明确归档查询语义并保持旧 full 结果所需字段，不能只替换 URL 就宣称兼容。
- task_id 不存在保持可识别的空结果；服务不可用、非 2xx、无效 JSON 不伪装成空任务。
- 仅有 session_id 的过滤移入服务端；无过滤列表沿用分页能力，明确总数、截断与下一页，不改变旧消费者而不告知。
- 摘要白名单保留身份、状态维度、当前/下一步、阻塞原因、Subject、必要模型来源及观测时间；长历史和证据正文走既有详情入口。
- 路由和 delegation 操作的 route_id、selected_model、claim_token 等执行字段不参与摘要裁剪。
- 顺带核对 `reportTaskProgress` 的单任务预读，避免只修查询工具留下相同的全量读取。

验收：单任务不请求全量列表；Session 交集正确；空结果与失败可区分；旧调用响应兼容；摘要关键问答完整；返回体不随无关任务数量增长。实施前确认具体参数名及分页兼容方案。

### U1 加载状态与新鲜度

沿用已有 15 秒可见页轮询，不引入 WebSocket。详情与活动各自保留 loading、error、最后成功数据和观测时间。切换任务不能显示上一个任务的内容；迟到响应不能覆盖当前任务。重新请求失败时，显示“读取失败”和旧数据时间，不宣称旧数据仍是最新。

首次成功且确实为空才显示“暂无活动/尚未提交证据”；字段缺失显示“未记录”，禁止从缺失推断业务未发生。验证、Review、验收继续分别展示。轮询共享节拍不等于原子快照，若数据修订不一致应允许说明观测差异，不新增快照协议。

验收：首次失败、刷新失败、成功空结果、切换任务、乱序返回、后台页面均有可区分行为；保留现有轮询刷新回归验证。

### U2 模型来源与工具活动

- 将 `selectedExecutorModel` 明确标为“路由选择”。实际运行模型只来自相应 run 的报告；无报告显示“未报告”，不拿配置补齐。
- 展示请求模型、报告模型和来源/时间；多次运行逐条关联，不取一条历史值充当当前事实。
- 主代理直接执行与 CLI 分开解释；没有 CLI run 不表示无人执行。
- 活动先使用已存 payload 提取工具名、可安全展示的动作摘要、结果和原因；缺字段就显示已知信息，保留类型作为兼容回退。
- 默认不复制完整命令输出、prompt、token、凭据和原始会话。无法安全摘要的输入只显示工具名及受控证据引用。
- 首批不调整计费/用量累加；同一事件跨 Hook/Runner 去重只有存在稳定关联依据时才做，不能按相似文本合并。

验收：仅选路由但未启动、启动失败、模型未知、多 run、主代理直接执行、事件字段缺失均不产生伪事实；恶意 HTML 以文本展示；敏感夹具不泄露。

## 6. 第二阶段：结果补报可靠性

### R0 先核查，避免重复建设

当前 `docs/delegated-cli.md` 已要求报告失败保留文件，由主会话补报；不是完全没有恢复。当前入口未显式传稳定 event_id，且在尝试网络回写后写最终输出。核查其他调用方、测试、部分成功记录和输出文件的现有消费者，确认哪些能力可复用。

本阶段重点是“结果补报”，不是任务重新执行，也不是让过期授权继续写代码。

### R1 推荐方案与待决策边界

推荐在已有运行包中保存不可变终态事实和稳定报告 ID，先持久化可恢复回执，再尝试回写；新增显式重报入口，仅重放同一回执。复用原 delegation 与 routing/result，不启动模型、不创建新任务、不隐式续租。不会部署后台恢复服务。

具体约束：

- delegation 结果和路由结果分别记录是否确认，部分成功只补未确认部分。
- 网络超时先按稳定 ID 查询/确认或幂等提交；同一 ID 不同内容拒绝并展示冲突。
- 已确认的终态回执不可被旧 running 回调覆盖。若需新增 attempt 标识，先审定兼容字段与旧记录语义。
- claim token 不进入可长期保存或提交 Git 的回执；现有临时 manifest 仍按原规则清理。
- TTL 到期或 delegation 撤销后，普通重报不得直接绕过授权。需要区分已接收事件的幂等重放与新历史证据接收；后者复用合法离线证据入口或经明确授权的补报策略，不能自行放宽 assertDelegate。
- 回执持久化失败应明确失败阶段；不能承诺消除进程退出到落盘之间的所有崩溃窗口。

替代方案：保留人工补报，仅提供明确错误与补报材料模板。成本低，但人工判定与事件 ID 管理仍易出错。推荐先以故障注入证明自动化入口的必要范围，再选择 R1。

验收矩阵：

| 注入场景 | 预期结果 |
| --- | --- |
| 执行成功，报告请求未到服务端 | 本地回执保留；只补报，不重跑 |
| 服务端已接收，响应丢失 | 重放不新增业务结果或重复事件 |
| delegation 成功，routing/result 失败 | 只补路由结果；执行结果不改写 |
| 相同 ID、不同内容 | 明确冲突，不静默覆盖 |
| 旧 running 晚于终态 | 不覆盖已确认终态 |
| TTL 到期/撤销后首次补报 | 现有权限拒绝或明确授权的历史证据路径，不续执行权限 |
| 回执文件写入失败 | 明确区分执行结果与保存失败，不伪称可恢复 |

## 7. 条件优化与暂缓项

### H1 Hook 判定解释

触发条件：有可复现误拦或客户端归一化不一致样本。先复用 `inspection-command.mjs` 和主 Hook，记录分类、规则、未识别片段与授权缺口；不给未识别命令贴“写入”标签，也不因此放行。

本轮 `rtk proxy sh -c` 包装读取被拒绝、直接只读命令通过，是解析边界样本，不自动证明授权规则错误。若扩大包装器解析，必须覆盖重定向、复合命令、环境赋值、子命令与真实写入反例，不以 `--version` 后缀放行全部命令。

验收以用户实际误拦夹具和安全反例为准，不追求零拒绝。共享分类器验证一次，各客户端重点验证归一化；不削弱各端已有边界。

### P1 同环境预检

触发条件：真实派发因安装、版本或协议差异失败。复用能力表，明确“已实现”与“当前可用”；路径、版本、协议、认证、额度、报告模型各有独立证据。探测与运行使用相同工作区和受控环境，但不保存完整环境变量。

只用受支持的无副作用接口；没有安全探测接口就显示 unknown，不读取认证文件，不启动模型试余额。能力探测不授予权限。每个 Harness 独立真实验证，不能以 Codex 测试推定其他客户端成功。

### D1 文档与证据处理

触发条件：现有文档派发反复出现缺文件、缺变量、路径或输出位置错误。先核对已有 manifest 校验，再在模型启动前完成确定性检查。只保存必要输入与指纹，重试传递增量；快照不能覆盖实时撤权。
