# 外部 Agent Review 注意事项

## 分工与边界

用户自行安排外部 Agent 审查及结果处理。实施 Agent 负责已授权的开发、验证和交付，不自动启动 OCR、不等待或轮询 Reviewer、不自动导入报告或处理 findings。审查可以在提交之后独立进行，不要求实施任务保持活跃。

所有任务的 Review 均不阻塞流程，包括 strict 和历史 required 合同；这些字段保留为历史记录和审查展示依据，不再作为完成前置条件。未审查、未覆盖、无法验证均如实记录，不因避免阻塞而写成通过。测试、权限与独立验收条件继续有效；不要伪造审查证据或自动处理外部发现。

## 开始前固定审查对象

- 明确仓库绝对路径、基线 commit、目标 commit、需求与验收条件；不要仅使用可能移动的分支名。
- 区分已提交 diff 与未提交修改。用户没给范围时先确认范围，不把其他人的改动混入结论。
- 阅读仓库 AGENTS.md、相关代码、调用方和测试。知识库帮助定位，当前代码与配置是事实来源；记录文档冲突。
- 默认只读。不修改代码、任务状态、配置或 Git 分支，不运行部署，不主动建立 TaskCenter 任务或申请 OCR 租约。

## 审查重点

先核对需求是否实现，再判断代码质量。重点检查实际失败路径，而不是只做样式建议：

- 任务状态与实际执行、验证、审查、验收是否区分；done_claimed 不等于最终验收。
- Session、task、delegation 的身份和所有权；不能用计划派发模型冒充实际执行模型。
- MCP、HTTP、Hook、账本投影之间的字段与语义一致性；同一行为的所有入口是否一致。
- 追加事件、幂等重试、并发冲突、部分失败、旧版本证据失效，以及合并后 Subject 的变化。
- 本地数据与凭据边界；禁止读取认证文件、上传 Session 正文或破坏健康服务。
- 测试是否覆盖用户真实路径、拒绝路径和恢复路径。测试通过不能替代对契约及根因的核对。

## 报告格式

报告交给用户即可，无需接入 TaskCenter 或等待实施 Agent 回应。

1. 审查对象：仓库、base/head SHA、需求来源。
2. 覆盖范围：实际检查文件、关键调用链、未覆盖部分及原因。
3. Findings：每项提供严重度、文件与行号、触发条件、证据、具体影响、最小修复建议及验证方式。
4. 验证：实际执行的命令与结果；未运行的检查明确标注，不能引用他人结果作为自己执行的结果。
5. 结论：发现问题、在已检查范围内未发现问题，或证据不足。说明置信边界。

严重度按影响区分：P0 为灾难性数据或安全风险，P1 为关键流程错误或高影响故障，P2 为一般正确性/可靠性问题，P3 为低影响建议。没有触发条件或影响证据的怀疑应单列为待核实，不作为已确认缺陷。避免为个人风格、假设性扩展或增加抽象而要求返工。

报告保留外部 Agent 的真实身份和已知模型；未知项写 unknown。不要冒充实施 Agent、内部 OCR Reviewer 或最终验收者。若用户以后明确要求机器导入，再按当时的接口契约准备数据，不自行编造 route_id、Session、费用或执行证据。
